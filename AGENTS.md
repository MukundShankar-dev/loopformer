# Agent guide

Read [README.md](README.md), then [docs/plan.md](docs/plan.md) for the current
scope. The user's explicit instructions set the scope; a planned future
milestone is not an instruction to build it now.

## Documentation: few files, fixed roles

The code is the source of truth. Docs explain what code cannot: purpose, how to
run it, what was found and why decisions were made. This repository has exactly
these docs:

| File | Role | How it changes |
| --- | --- | --- |
| `README.md` | What this is, quick start, links. 40 lines or fewer. | Rarely |
| `docs/plan.md` | Current goals, milestones, gates, open decisions | Edited in place when the plan changes; never appended with amendments |
| `docs/architecture.md` | How the current code works: shapes, semantics, contracts | When behaviour described there changes |
| `docs/usage.md` | Commands that run each workflow | When a command or flag changes |
| `docs/setup.md` | Environments and machines | When dependencies or machines change |
| `docs/history.md` | The single log of what was done, results, decisions and dead ends | One short dated entry per milestone or experiment |

Rules:

- **Do not create new Markdown files** unless the user asks. Put the content in
  the file whose role fits, or leave it out.
- **Each fact lives in one place.** Other files link to it; never restate it.
  Numbers appear only in `docs/history.md` (or a results file generated by
  code), never copied into the README, plan or architecture.
- **Update only the file whose role the change affects.** A code change usually
  touches zero or one doc. Do not make "status" edits across several files.
- **A history entry** has the date, what was done and why (1–3 lines), the
  exact command, the outcome with key numbers, artifact paths, and the commit.
  Write it once, when the work is done. Fix a wrong entry in place and say so;
  do not append contradicting paragraphs.
- **State each limitation once**, next to the claim it limits. Don't repeat
  boilerplate caveats ("X remains closed", "not yet confirmed") across files.
- **Never describe planned or unrun work as done.** Mark planned items in
  `docs/plan.md` only.
- **Generated reports go next to their artifacts** (for example
  `eval/<run>/report.md`). Code must never edit files under `docs/`.
- Prefer deleting stale text over adding text that corrects it.

## Code conventions

- Write modular, minimal, readable code. Each module and function has one clear
  responsibility; prefer direct control flow and descriptive names.
- Keep model mechanics, data generation, training objectives, evaluation and
  CLI entry points separate. CLIs compose library functions. Shell launchers
  live in `scripts/launch/`.
- Implement only what the current milestone needs. No speculative frameworks,
  wrappers or duplicated logic. Reuse existing evaluators and metrics instead
  of building parallel ones.
- Make configuration explicit. No hidden global state, import-time model
  loading, implicit downloads, or silent device/dtype changes.
- Type-hint public interfaces. Document tensor shapes, loop indexing, target
  semantics and non-obvious gradient behaviour. Comments explain reasons, not
  what the code says.
- Validate at boundaries and fail with useful errors. Never catch broad
  exceptions to hide failures.
- Use Rich for terminal output; save machine-readable results separately.
- Test contracts: equivalence, parameter sharing, gradient scope, exact
  targets, metric correctness, and that each test can fail. A test that passes
  on an untrained or unchanged model proves nothing. A test of a failure path
  checks the specific error, not just a nonzero exit.
- Keep changes focused, preserve unrelated user work, and report what was
  checked and what was not.

## Experimental discipline

- Keep development and confirmation data separate. Choose thresholds,
  checkpoints and hyperparameters on development data; freeze them before
  confirmation; open confirmation once per final candidate.
- Run at least three independent training seeds before stating a headline.
  Run the ablations for a component in the milestone that introduces it.
- Compare at matched compute and say what was matched. Separate quality gains
  from compute savings; offline oracle savings are not measured speedups.
- For latency, synchronize the device, exclude warmup, and state the timing
  scope.
- Record negative results in `docs/history.md`.
- Before a design change that alters what a result means, explain the
  consequence and record the decision in `docs/history.md`.

## Machines

- Mac (Apple Silicon, 32 GB): development and CPU tests.
- Desktop (`ssh desktop`, WSL2, RTX 5070 Ti 16 GB, about 16 GB RAM visible to
  WSL): GPU work.
  - The desktop is shared with other projects. Before starting work, check
    `nvidia-smi` (at `/usr/lib/wsl/lib/`) and the load average, run
    CPU-heavy jobs under `nice`, and cap threads.
  - Work in a separate git worktree rather than the desktop's main checkout,
    which may contain the user's uncommitted work.
